# Дополнительные функции CarLife: звук, навигация и голос

[English](../CARLIFE_SERVICES.md) · [Аудиокандидат](AUDIO_CANDIDATE.md)

Смешанный MEDIA-источник и приём аудио на HU реализованы и проверены офлайн. Звук на устройстве пока не подтверждён. Раздельное аудио, навигационные метаданные и голос ниже — следующие изменения, а не уже установленные функции. Рабочий baseline видео и ввода сохраняется.

## Порядок работы

1. **Получить слышимый звук Android на ГУ:** установить текущий кандидат, включить известную запись, проверить переключение на радио, остановку и переподключение. Использовать существующие USB transport и writer.
2. **Отделить подсказки от музыки:** добавить источник с маршрутизацией Android audio и пакеты TTS. Проверить настоящую подсказку Яндекса поверх музыки и радио. Третий выходной канал VR для этого не требуется.
3. **Добавить управление и данные:** кнопки/метаданные Android MediaSession, манёвры Яндекса и микрофон ГУ для штатного ассистента. Эти части можно разрабатывать независимо; завершение всех остальных сервисов не является условием начала каждой из них.

Ускорение загрузки также не зависит от звука. Бокс и ГУ нужны для проверки слышимости, реальных данных приложений и времени старта, но не для реализации протокола и тестов на Mac. Новая прошивка, AA/DHU-сессия или дополнительный фреймворк не нужны как предварительный этап.

## Источники и назначения

| Функция | Источник Android | CarLife | Статус |
| --- | --- | --- | --- |
| Launcher, карта, приложения | Существующий EGL/MediaCodec | VIDEO channel 2 | Принятый baseline |
| Музыка и пока общий смешанный звук | REMOTE_SUBMIX PCM | MEDIA channel 3 | Кандидат реализован |
| Подсказки и ответы ассистента | Отдельные маршруты звука приложений | Сначала TTS channel 4 | План |
| Микрофон ГУ | HU channel 5 / `0x58001` | Вход штатного recognizer/ассистента | План |
| Манёвр, дорога, расстояние | Адаптер **Яндекс Навигатора / Яндекс Карт** | CMD navigation | Требуется посмотреть данные приложения |
| Трек, прогресс и кнопки воспроизведения | Активная Android MediaSession | CMD metadata / MediaController | План |

HeadSwap v1.2.0 получает отдельные MEDIA и SPEECH из AA: музыка идёт в channel 3, **подсказки и ответы ассистента — в TTS channel 4**. Та же схема CarLife подходит для наших штатных источников Android. Вход микрофона по channel 5 не требует ответа ассистента по channel 5. Отдельный выход VR можно добавить при конкретной необходимости на ГУ. [Исходник AaBridge](https://github.com/YegorkaPomidorka/headswap/blob/0f5502ab76e2f220b68fa1e2c85b66838f01fd81/android/app/src/main/java/com/yegorkapomidorka/headswap/aa/AaBridge.kt).

## Разделение Android-аудио у источника

Кандидатный механизм — привилегированная **AudioPolicy**, PLAYERS **AudioMix** с `ROUTE_FLAG_LOOP_BACK` и `AudioPolicy.createAudioRecordSink(mix)`. У маршрутов отдельные адреса. Начальные правила выбирают MEDIA usages UNKNOWN=0 / MEDIA=1 / GAME=14 и навигационный ASSISTANCE_NAVIGATION_GUIDANCE=12. ASSISTANT=16 можно добавить в речевой маршрут или отдельный sink, если требуется управление одновременной речью; сначала оба используют TTS на USB. Расширяются существующие audio worker/writer.

Чистый LOOP_BACK перенаправляет выбранное воспроизведение; LOOP_BACK|RENDER копирует его и имеет другие ограничения захвата. Публичный AudioPlaybackCapture ограничен подходящим MEDIA/GAME/UNKNOWN. `allowPrivilegedPlaybackCapture(true)` имеет ограничения качества и не решает задачу полноценного навигационного звука. [Документация Android](https://developer.android.com/media/platform/av-capture), [AudioPolicy](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/media/java/android/media/audiopolicy/AudioPolicy.java), [native rules](https://android.googlesource.com/platform/frameworks/av/+/android-15.0.0_r1/services/audiopolicy/common/managerdefinitions/src/AudioPolicyMix.cpp).

В предоставленном OEM framework реализованы эти API и remote submix. Регистрация проверяется с имеющимся привилегированным runtime; нужное разрешение маршрутизации — `MODIFY_AUDIO_ROUTING`. Наличие API не доказывает работу маршрута, но заранее требовать патч прошивки/HAL оснований нет. Короткий тест двух различимых тонов от одного UID с разными usages покажет, получает ли каждый sink только свой звук.

Правила уточняются по настоящим playback attributes Яндекса. Приложение может помечать речь как MEDIA или проигрывать её отдельным сервисом. UID/session полезны, когда действительно выделяют нужный звук; анализ громкости и копирование одного PCM в два канала разделения не дают. AudioMix объединяет разные измерения правил через AND, а значения одного измерения — через OR. Явный выбор устройства самим приложением может иметь приоритет над динамическим mix, поэтому после двух тонов проверяется реальное воспроизведение.

Регистрацией и освобождением маршрутов управляет один владелец. Перед включением раздельного режима закрывается общий захват address 0. При ошибке регистрации видео/тач остаются доступны, причина аудиоошибки записывается; возврат к общему захвату выполняется после удаления созданных маршрутов. Расширяются существующие ограниченные очереди и единственный USB writer.

Поведение воспроизведения:

- MUSIC отражает активную музыку. Кандидат останавливает захват при выборе радио и отправляет Android MEDIA_PAUSE; новое событие воспроизведения музыки или явный MEDIA_PLAY возвращает PCM. Опрос MUSIC=1 не отменяет выбор радио. Известный idle не посылает MEDIA_INIT/PCM. Клавиши media/DPAD уже сопоставлены с Android; адресное управление через MediaController и метаданные остаются следующими изменениями. Повтор VIDEO_START не означает Play.
- Речь передаётся как INIT → PCM → STOP, без постоянно активного тихого TTS. Подсказки и ответ ассистента сначала воспроизводятся по очереди.
- Конец подсказки не отменяет текущий маршрут. Два основания для NAVI status хранятся отдельно в существующей сессии; новый coordinator-фреймворк не требуется.
- До дополнительного приглушения на ГУ учитывается Android audio focus. Возобновляется только ранее игравшая музыка, которую пользователь не остановил.

## Микрофон ГУ и штатный голосовой ввод

Начало голосовой сессии приходит как VR module 4 в `MODULE_CONTROL 0x18028` либо поддержанный VR hardkey. MD запрашивает запись `0x10024`; HU возвращает channel 5 / `0x58001`; завершение — `0x10023`. Начальный формат 16 кГц mono PCM16 сверяется с пакетами ГУ. AA ACK/окна и пропуск первых пакетов здесь не нужны.

Для существующего ассистента/клавиатуры кандидат — INJECTOR AudioMix с LOOP_BACK и `AudioPolicy.createAudioTrackSource(mix)`. Выбираются фактический UID recorder и capture preset; session ID добавляется, если нужно различать одновременные записи. Этот путь реализован в OEM framework. Нужно определить настоящий recording service, зарегистрировать маршрут до открытия recorder и вызвать обычное Android-действие голосового ввода. Поздний attach не считается гарантированным перенаправлением любой уже открытой записи. [AudioMixingRule](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/media/java/android/media/audiopolicy/AudioMixingRule.java).

Микрофонный маршрут можно проверять отдельно, до раздельного выхода. Позже он использует общего владельца policy. Инъекционный трек имеет `USAGE_VIRTUAL_SOURCE=15`, исключённый из выходных sinks. Ограниченная очередь и worker передают PCM без блокировки USB reader; cancel/disconnect заканчивает запись ГУ и освобождает track/маршрут. Сначала проверяется нужный recorder и контрольный recorder, затем настоящая фраза и ответ ассистента через TTS. Первый режим — push-to-talk; эхо и barge-in улучшаются отдельно.

Для собственного голосового интерфейса API 33+ [RecognizerIntent.EXTRA_AUDIO_SOURCE](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE) принимает PCM pipe и формат. Это более простой вариант при поддержке выбранным recognizer; проверяется использование именно переданного PCM. Он не подменяет вход любых приложений. Разрешения записи и mic privacy сохраняются. Собственный TTS может отдавать PCM через [UtteranceProgressListener](https://developer.android.com/reference/android/speech/tts/UtteranceProgressListener); один синтез не надо проигрывать и захватывать повторно.

## Навигация из Яндекс Навигатора / Карт

Карта, подсказки и данные манёвра — независимые функции. Первый адаптер читает установленный **Яндекс Навигатор / Яндекс Карты**, через доступный интерфейс приложения или навигационные уведомления. По короткому настоящему маршруту реализуются доступные поля, остальные манёвры и версии добавляются постепенно. Полный каталог fixtures не требуется до первого работающего адаптера. Отсутствующие данные остаются неизвестными.

`NotificationListenerService` даёт уведомления после разрешения доступа, но `CATEGORY_NAVIGATION` не определяет обязательные поля манёвра/расстояния. Яндекс NaviKit предоставляет guidance внутри приложения с SDK, а не читает маршруты установленного Навигатора/Карт. AndroidX `NavigationManager.updateTrip` также отправляет данные своего приложения, а не читает чужие. [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [Yandex guidance](https://yandex.com/maps-api/docs/mapkit/android/generated/navigation/guidance.html), [NavigationManager](https://developer.android.com/reference/androidx/car/app/navigation/NavigationManager).

Первая реализация небольшая: адаптер Яндекса передаёт текущий маршрут/манёвр/расстояние существующей CarLife-сессии и CMD writer. Обновления расстояния объединяются, новые повороты и конец маршрута сохраняются, потеря источника очищает устаревшие данные, после reconnect и подписки передаётся свежий снимок. Отдельный provider/coordinator-фреймворк нужен только если его потребуют несколько настоящих источников.

Подписки: `0x18043` / ответ `0x10044`, START `0x18045`, STOP `0x18046`. Navigation subscription ID — **0**, функциональный NAVI module ID — **2**. Манёвр передаётся как `NAVI_NEXT_TURN_INFO=0x10030`; место его отображения выбирает ГУ. Одна подписка не доказывает работу приборки/HUD.

Старый Baidu proto использует required **int32 time** в поле 6; новый анализ Baidu — **bytes turnIconData**. HeadSwap по умолчанию использует **BOTH**. Выбираем такой же совместимый вариант: при наличии иконки передаём оба wire types, сохраняя поле времени. Стандартный protobuf parser читает известный тип и пропускает другой; локальная проверка подтвердила BOTH на обеих required-схемах в обоих порядках. TIME/ICON остаются overrides на случай фактической несовместимости ГУ. Отдельный захват эталонной сессии не является условием начала реализации. [Старый proto](https://github.com/milesking/apollo-DuerOS/blob/6a07419818f46aadda34c5f55e63d4a1fc8136ef/CarLife-Vehicle-Lib/LibSource/protobuf/proto/CarlifeNaviNextTurnInfoProto.proto), [исследование HeadSwap](https://github.com/YegorkaPomidorka/headswap/blob/0f5502ab76e2f220b68fa1e2c85b66838f01fd81/docs/cluster-metadata-recon.md), [protobuf wire format](https://protobuf.dev/programming-guides/encoding/).

Метаданные объявляются поддержанными после подключения настоящего источника и кодировщика, а не только из-за подписки ГУ. На ГУ проверяются реальные манёвры, отмена маршрута и reconnect; приборка/HUD — отдельно при наличии. Эти проверки не задерживают первый работающий музыкальный выход.
