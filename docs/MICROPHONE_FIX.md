## What changes

- `NativeMicrophone` observes active Android recording sessions and creates a separate input AudioPolicy for the exact application UID, capture source and audio session. It requests the HU microphone only after Android reports that recorder on the injector's own remote-submix address. It does not restart the existing music/speech capture policy.
- HU channel 5 / `0x58001` PCM16 mono 16 kHz enters a bounded queue, then an AudioTrack injector. USB reception never waits for audio writes. Old route generations and stale PCM are discarded; closing the recorder/session releases the route.
- Mic-test3 keeps AudioTrack's platform buffer instead of forcing 320 frames. The reference device reports 4,104 frames; this is a measured value, not a portable hardcoded requirement. The prior small-buffer run lost substantial PCM and is retained as a failed attempt.
- Mic-test4 explicitly exits the boot-native process after the existing session/controller cleanup and bounded log flush. The Android framework's non-daemon `AudioPortEventHandler` had kept the old process alive after main returned. A completed controller with a released capture lease exits 0; controller/cleanup failure or a retained lease exits 1. DEV behavior is unchanged. Two subsequent device sessions confirmed exit and rearm; the prior failure remains part of the evidence. Voice launch intents/URIs are unchanged.
- Shared microphone demand keeps one HU stream for ordinary application recording and the optional explicit recognizer. `0x10024` starts the first consumer; `0x10023` stops the last. Finishing one consumer does not stop the other. Ordinary app recording does not announce a VR assistant as busy.
- By default, the voice action requests an installed voice UI, trying `VOICE_COMMAND`, voice `WEB_SEARCH`, then `ASSIST`. It does not require Google or the MD's own SpeechRecognizer. Actual recording remains owned by that application. An Activity launch alone is **not** evidence of microphone delivery.

The existing privileged runtime supplies routing access; the application's normal recording permission and microphone privacy rules still apply. No extra app, AA bridge or playback backend is introduced. `USAGE_VIRTUAL_SOURCE=15` is excluded from MEDIA/TTS capture, preventing the injected input from being captured as output again. Calls, Bluetooth microphone bridging and echo cancellation are not qualified by this change.

## Build and check in order

Build through the existing [MD recipe](BUILD_MD.md), which runs the JVM suites; use its pinned toolchain. Package the resulting JAR through the existing [runtime build](BUILD_RUNTIME.md) and [runtime updater](MAGISK_RUNTIME_UPDATE.md), retaining the installed runtime version and enabled native services. Do not start a second MD beside the installed controller.

After installing a candidate on the supported existing installation, keep an ADB connection and collect read-only diagnostics on the host (`SERIAL` is the already-authorized ADB serial):

```sh
adb -s "$SERIAL" shell "su -c 'sha256sum /data/local/carlife-native/versions/boot-native-v1-20261014/md.jar'" > md-sha256.txt
adb -s "$SERIAL" shell dumpsys audio > audio.txt
adb -s "$SERIAL" shell dumpsys media.audio_policy > audio-policy.txt
adb -s "$SERIAL" exec-out "su -c 'tar -C /data/local/carlife-native -cf - logs'" > md-logs.tar
```

1. With native CarLife connected, open voice input **inside Yandex**. Confirm `native_microphone: route_created` followed by `route_verified` for that UID/source/session. `route_not_applied` means the existing recorder was not rerouted; do not count it as working.
2. Confirm `mic_demand=true`, transmitted `0x10024`, received `0x58001`, and increasing `written_pcm_bytes`. Inspect `pcm_peak`, `pcm_rms`, `queued_pcm_bytes`, `dropped_pcm_bytes`, `invalid_packets` and `pcm_write_error`. Counters do not substitute for a phrase recognized from the HU microphone.
3. Close voice input, repeat it, and reconnect CarLife. Check `route_closed` with `cleanup=true`, last-consumer `0x10023`, no stale route, and continued video/music. Also confirm the old MD PID actually exits, the controller rearms discovery, and a new session receives video. A `stopped` log by itself is insufficient. Then test the HU voice button separately: `voice_ui_launched` with `recording_started=false` proves only launch; the recorder/PCM checks are still required.
